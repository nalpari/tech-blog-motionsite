## 쉬운 단계별 가이드 ✨

Spring Boot 애플리케이션을 처음 시작하면 모든 것이 원활하게 작동합니다. 하지만 대규모 트래픽에서는 기본 설정만으로는 충분하지 않습니다. **초당 100만 건의 요청(RPS)** 을 처리하는 것은 정밀한 튜닝, 효율적인 코딩, 그리고 신중한 인프라 설계가 필요한 높은 목표입니다. 💪

이 가이드는 Spring Boot를 극한의 수준으로 확장하는 데 필요한 중요한 최적화를 안내합니다. 트래픽이 많은 전자상거래 이벤트, 글로벌 SaaS 워크로드 또는 미션 크리티컬 API를 준비하고 있다면 여기에서 실용적인 인사이트를 찾을 수 있을 것입니다.

---

## 1️⃣ 규모 문제 이해하기

100만 RPS를 처리하는 것은 단순히 Spring Boot만의 문제가 아니라 전체 시스템의 문제입니다. 이 수치에 도달하려면 다음이 필요합니다:

- **효율적인 코드 실행** 🎯 - 요청당 낮은 CPU 및 메모리 오버헤드
- **최적화된 I/O** ⚡ - 가능한 한 논블로킹 방식
- **수평 확장성** 📈 - 여러 노드, 로드 밸런싱
- **효율적인 데이터 처리** 💾 - 캐싱, 비동기 작업, 최소한의 DB 병목 현상

Spring Boot를 퍼즐의 한 조각으로 생각하세요. 런타임 환경, JVM 및 인프라도 똑같이 중요합니다.

---

## 2️⃣ 올바른 Spring Boot 아키텍처 선택하기

기본적으로 Spring Boot는 내장된 Tomcat 서버를 사용합니다. 신뢰할 수 있지만 **Tomcat은 블로킹 I/O(BIO) 기반**이므로 처리량이 제한됩니다. 대규모에서는:

- **Netty로 전환하기** 🔄 - Spring WebFlux를 통해 Netty를 사용하세요. Netty는 논블로킹 I/O를 사용하며 더 낮은 메모리 오버헤드로 훨씬 더 많은 동시 연결을 처리할 수 있습니다.
- **리액티브 프로그래밍 고수하기** ⚛️ - `Mono`, `Flux` 및 백프레셔를 사용하여 스레드 고갈을 방지하세요.

Tomcat을 사용해야 한다면 많이 튜닝해야 하지만, 진정한 100만 RPS를 위해서는 **WebFlux + Netty**가 더 현명한 경로입니다.

---

## 3️⃣ 스레드 관리 최적화하기

Spring Boot의 성능은 스레드 구성과 밀접하게 연결되어 있습니다:

### 🔧 Tomcat 튜닝 (Tomcat 사용 시):

```
server.tomcat.max-threads=1000
server.tomcat.accept-count=10000
server.tomcat.connection-timeout=20000

```

### ⚙️ Netty 튜닝 (WebFlux):

Netty는 이벤트 루프로 스레드를 관리하므로 더 적은 스레드가 필요합니다. 대신 블로킹 호출을 피하는 데 집중하세요.

### ⚠️ 컨트롤러 내부에서 블로킹 호출 피하기

단일 블로킹 DB 또는 HTTP 호출이 이벤트 루프를 막을 수 있습니다.

**경험 법칙**: 더 많은 스레드 ≠ 더 많은 처리량. 확장성을 극대화하려면 비동기 및 리액티브 호출을 사용하세요. 🎪

---

## 4️⃣ JVM 및 GC 튜닝

JVM은 Spring Boot의 엔진입니다. 기본값은 안전하지만 높은 RPS에 최적화되어 있지 않습니다.

### 🎯 주요 JVM 최적화:

- **최신 JDK 사용(17 이상)** ☕ - 각 릴리스는 성능과 메모리 효율성을 향상시킵니다.
- **올바른 가비지 컬렉터(GC) 선택**:
    - **G1GC** - 균형 잡힌 워크로드용
    - **ZGC** 또는 **Shenandoah** - 초저지연용
- **메모리 할당** 💻 - 힙 크기를 명시적으로 설정:
    
    ```bash
    -Xms4g -Xmx4g -XX:+UseG1GC
    
    ```
    
    - 컨테이너 제한에 따라 조정
- **컨테이너 인식 활성화**:
    
    ```bash
    -XX:+UseContainerSupport
    
    ```
    

잘 튜닝된 GC는 100만 RPS에서도 지연 시간을 예측 가능하게 유지합니다. ⏱️

---

## 5️⃣ 적극적으로 캐싱 활용하기

데이터베이스와 외부 서비스는 **가장 큰 병목 현상**입니다. 극단적인 규모에서는 모든 요청마다 이들을 호출할 여유가 없습니다. 🚫

### 📦 캐싱 전략:

- **인메모리 캐싱(Caffeine)** - 로컬, 근거리 캐시 성능
- **분산 캐싱(Redis, Hazelcast, Memcached)** - 다중 노드 환경용
- **HTTP 응답 캐싱** - 가능한 경우 정적 응답 캐시
- **데이터베이스 쿼리 캐싱** - Hibernate의 2차 캐시 또는 사용자 지정 캐싱 전략 사용

**황금 법칙**: 모든 요청마다 데이터베이스를 절대 호출하지 마세요! 🏆 적절한 캐싱을 사용하면 DB가 병목 현상이 아닌 백업이 됩니다.

---

## 6️⃣ 데이터베이스 상호작용 최적화하기

Spring Boot 앱이 관계형 데이터베이스에 의존하는 경우:

### 🔗 데이터베이스 최적화:

- **커넥션 풀링 사용**(HikariCP는 Spring Boot의 기본값)
- HikariCP를 높은 처리량으로 튜닝:
    
    ```
    spring.datasource.hikari.maximum-pool-size=200spring.datasource.hikari.minimum-idle=50spring.datasource.hikari.idle-timeout=30000spring.datasource.hikari.max-lifetime=600000
    
    ```
    
- 단일 쿼리보다 **배치 삽입/업데이트** 선호 📊
- **분석 쿼리**를 복제본으로 오프로드 🔄
- 초고속 쓰기/읽기 워크로드를 위해 **NoSQL(Cassandra, DynamoDB, MongoDB)** 고려 ⚡

100만 RPS에서 DB는 단순한 데이터베이스가 아니라 **분산 시스템**입니다. 이에 맞게 설계하세요. 🌐

---

## 7️⃣ 직렬화 오버헤드 최소화하기

직렬화 및 역직렬화는 대규모에서 조용한 킬러입니다. JSON은 사람에게 친숙하지만 CPU 집약적입니다. 😰

### 🎨 최적화:

- **Jackson Afterburner** 사용으로 JSON 직렬화 속도 향상 🚀
- 클라이언트와 서버 모두 지원하는 경우 **바이너리 형식(Protobuf, Avro, Smile)** 선호
- 네트워크가 병목 현상인 경우에만 응답 압축. 그렇지 않으면 압축이 CPU를 소모합니다.

작은 직렬화 변경으로 처리량을 두 배로 늘릴 수 있습니다! 💯

---

## 8️⃣ 수평 확장으로 배포하기

단일 Spring Boot 인스턴스로는 100만 RPS를 처리할 수 없습니다. 수평으로 확장하세요:

### ☸️ 확장 전략:

- **Kubernetes + HPA(Horizontal Pod Autoscaler)** - CPU/메모리 또는 사용자 지정 메트릭(RPS, 지연 시간)을 기반으로 확장
- **서비스 메시(Istio/Linkerd)** - 트래픽, 재시도 및 서킷 브레이킹 관리
- **무상태 설계** 🎭 - 세션 데이터를 Redis 또는 데이터베이스에 보관하고 메모리에는 절대 보관하지 마세요.

서버가 아닌 **클러스터 관점**으로 생각하세요. 🌟

---

## 9️⃣ 비동기 메시징 및 이벤트 기반 아키텍처 활용하기

극한의 부하에서는 동기 요청-응답 시스템이 어려움을 겪습니다. **비동기 파이프라인**을 도입하세요:

### 📮 비동기 전략:

- **Kafka, RabbitMQ, Pulsar**를 사용하여 분리된 이벤트 처리 🎪
- 무거운 작업(이미지 처리, 분석, 알림)을 비동기 큐로 오프로드
- 작업이 백그라운드에서 계속되는 동안 클라이언트에 즉각적인 응답 반환 ⚡

이 패턴은 앱을 과부하시키지 않으면서 높은 요청 처리량을 유지하는 데 도움이 됩니다.

맹목적으로 최적화할 수는 없습니다. 실제 메트릭을 사용하세요:

### 📊 도구 및 메트릭:

**부하 테스트 도구**: Gatling, JMeter, Locust
**프로파일러**: YourKit, JFR(Java Flight Recorder), async-profiler
**모니터링**: Micrometer + Prometheus + Grafana

### 🎯 주시할 주요 메트릭:

- 응답 시간(p95, p99 지연 시간) ⏱️
- GC 일시 중지 🗑️
- CPU 사용률 💻
- DB 쿼리 시간 📊

모니터링 없이는 100만 RPS에 정말로 준비되었는지 알 수 없습니다.
